# راه‌انداز: همکار فنی صاحبان وب‌سایت روی لیارا

**راه‌انداز** یک دستیار هوشمند (AI Agent) برای چرخه‌ی کامل یک وب‌سایت روی لیاراست: از اولین دیپلوی و انتخاب پلن تا اتصال دامنه، انتشار نسخه‌های جدید، پایش سلامت و منابع، تحلیل لاگ، تشخیص علت مشکل و اصلاح آن با تأیید کاربر. کاربر هدف، برنامه‌نویسی است که «هیچ‌چیز از دیپلوی نمی‌داند». نام دستیار در گفتگو «راهی» است.

- مخزن: `amirhosein3000/rahandaz` · اجرا: `pnpm install && pnpm dev` ← `http://localhost:3200`
- این سند به‌خواست چالش شامل این بخش‌هاست: معماری کوتاه، نحوه‌ی اتصال به APIهای لیارا، محدودیت‌ها و نحوه‌ی تعامل کاربر.

---

## ۱. نحوه‌ی تعامل کاربر با سیستم

کاربر فقط سه کار می‌کند: **درخواستش را به زبان ساده می‌نویسد، پیشنهادها را می‌خواند، و برای تغییرها «تأیید» می‌زند.**

| کاربر می‌گوید | دستیار چه می‌کند |
|---|---|
| «این پروژه را دیپلوی کن: لینک گیت‌هاب» | پروژه را می‌شناسد (زبان، فریم‌ورک، پورت، متغیرها، نیاز به دیتابیس)، **نقشه‌ی فارسی با پلن و هزینه‌ی ماهانه** می‌دهد، بعد از تأیید اپ را می‌سازد و دیپلوی می‌کند، لاگ بیلد را زنده نشان می‌دهد، اگر خطا داد علت را با استناد به مستندات لیارا پیدا و اصلاح (diff) را پیشنهاد می‌کند و تا سالم شدن ادامه می‌دهد |
| «سایتم کند شده» / «خطای ۵۰۰ می‌دهد» | **گزارش SRE**: آزمایش آدرس، CPU و RAM، تحلیل لاگ ۳۰ دقیقه‌ی اخیر (نرخ خطا، زمان پاسخ، خطاهای تکراری)، ریلیزها؛ **علت‌های احتمالی به ترتیب احتمال با شاهد**، پیشنهاد اصلاح، اجرای آن با تأیید و **بررسی دوباره و مقایسه‌ی قبل/بعد** |
| «دامنه‌ی myshop.ir را وصل کن» | دامنه را به اپ وصل می‌کند، DNS و رکوردها را روی DNS لیارا می‌سازد، **تنها کار بیرون از دسترس (تغییر NS در ایرنیک)** را با مقادیر دقیق و دکمه‌ی کپی به کاربر می‌سپارد، بعد از «انجام دادم» بررسی می‌کند و SSL صادر می‌کند |
| «نسخه‌ی جدید را منتشر کن» | آخرین کد مخزن را روی همان اپ منتشر می‌کند و سلامتش را چک می‌کند (یک کلیک از صفحه‌ی اپ‌ها) |
| «استقرار خودکار با هر push» | فایل GitHub Actions مطابق مستند CI/CD لیارا را می‌سازد و دو قدم کاربر را مشخص می‌کند |
| «چه کارهایی نمی‌توانی؟» | فهرست صریح قابلیت‌ها و محدودیت‌های API (صفحه‌ی «قابلیت‌ها») |

**نمایش وضعیت عملیات:** بالای هر کار یک نوار مرحله (مثلاً شناخت پروژه ← نقشه و هزینه ← استقرار ← رفع خطا ← بررسی سلامت) با کار در حال انجام و زمان سپری‌شده؛ در کنار آن «جزئیات فنی» شامل هر ابزار، لاگ‌ها و فراخوانی‌های دقیق API.

**سه سطح ریسک (Human-in-the-Loop):**

| سطح | نمونه | رفتار |
|---|---|---|
| خودکار · بی‌خطر | خواندن لاگ، متریک، وضعیت، جستجوی مستندات، گزارش SRE | بدون پرسیدن اجرا می‌شود |
| نیازمند تأیید | ساخت اپ، دیپلوی، تنظیم متغیر، ری‌استارت، تغییر پلن، اتصال دامنه، SSL | کارت تأیید با شرح، فراخوانی‌های دقیق API، هزینه، **راه برگشت** |
| حساس · تأیید دوم | حذف یا خاموش‌کردن اپ، بازنویسی متغیر موجود | کاملاً غیرفعال مگر `ALLOW_DESTRUCTIVE=true`؛ و حتی آن‌وقت باید **نام منبع تایپ شود** |

کانال‌های تعامل: **کنسول وب** (فارسی، راست‌به‌چپ، موبایل و دسکتاپ)، **خط فرمان** (`pnpm cli`)، **ربات بله/تلگرام** (تأیید با دکمه‌ی چت؛ رمزها هرگز در چت خواسته نمی‌شوند).

## ۲. معماری کوتاه

```
 کنسول وب (Next.js)   CLI   ربات بله/تلگرام
          \             |          /
           ▼            ▼         ▼
   AgentRuntime: حلقه‌ی ابزارمحور LLM ⇄ ابزارها
        │  هر فراخوانی ابزار ← لایه‌ی سیاست (Policy) ← اجرا | پرسیدن از کاربر | مسدود
        │  تحلیلگر پروژه · برنامه‌ریز و هزینه · درمانگر خطا · ایجنت SRE · جستجوی مستندات
        │  گاوصندوق رمزها · پاک‌کننده‌ی رمز از خروجی · دفاع prompt injection · گزارش ممیزی زنجیره‌ای
        ▼
   LiaraClient ── RealLiaraClient (REST روی APIهای واقعی لیارا)
               └─ MockLiaraClient (لیارای شبیه‌سازی‌شده برای دمو و تست)
```

- **مدل زبانی:** Liara AI (با اعتبار لیارا) یا هر سرویس سازگار با OpenAI؛ دومی پشتیبان خودکار اولی است. حالت `MOCK_LLM` یک «مغز» قطعی دارد که به نتیجه‌ی واقعی ابزارها واکنش نشان می‌دهد (برای دموی آفلاین و تست).
- **ابزارها** (۲۰+): هر کدام با schema نوع‌دار (zod) و برچسب ریسک. **قوانین ایمنی در کد اعمال می‌شوند، نه در prompt:** تأییدها به فراخوانی دقیق (هش ابزار و آرگومان‌ها) گره خورده‌اند و یک‌بارمصرف‌اند؛ فقط از کانال کاربر ساخته می‌شوند.
- **ایجنت SRE:** تحلیل قطعی و سریع (بدون نیاز به LLM) از سیگنال‌ها: ۸ بررسی چراغ‌راهنمایی، تشخیص نشانه (قطعی، خطا، کندی، منابع)، فرضیه‌های رتبه‌بندی‌شده با شاهد، اقدام پیشنهادی یا راهنمای گام‌به‌گام، محدودیت‌های API، و مقایسه‌ی قبل/بعد.
- **دانش لیارا:** جستجوی BM25 فارسی (به‌اضافه‌ی جستجوی برداری اختیاری) روی ۳٬۷۳۵ تکه از مستندات لیارا؛ برگرفته از پروژه‌ی قبلی ما LiaraYar. هر تشخیص به صفحه‌ی مستند مرتبط لینک می‌دهد.
- **ایمنی:** `DRY_RUN` (فقط نمایش فراخوانی‌ها)، سقف بودجه‌ی ماهانه، فهرست اپ‌های مجاز (`ALLOWED_APPS`)، سقف گام، سقف توکن و timeout، گزارش ممیزی append-only با زنجیره‌ی هش، و رمز عبور کنسول به‌همراه محافظت CSRF.

## ۳. نحوه‌ی اتصال به APIهای لیارا

- احراز هویت: `Authorization: Bearer <LIARA_API_TOKEN>`؛ برای تیم‌ها `?teamID=`. توکن فقط سمت سرور است و از همه‌ی خروجی‌ها پاک می‌شود.
- منبع حقیقت: [OpenAPI رسمی لیارا](https://github.com/liara-cloud/openapi) (نسخه‌ی ذخیره‌شده در `docs/liara-api/spec`)، خروجی `liara --help` و سورس `@liara/cli`. فهرست کامل endpointها و منبع هر کدام در [`docs/liara-api/NOTES.md`](liara-api/NOTES.md). هر چه تأیید نشده با برچسب `UNVERIFIED` آمده است.

| کار | endpoint |
|---|---|
| فهرست و جزئیات اپ‌ها | `GET /v1/projects`, `GET /v1/projects/{name}` |
| ساخت اپ / تغییر پلن / ری‌استارت / روشن‌خاموش | `POST /v1/projects`, `/resize`, `/actions/restart`, `/actions/scale` |
| دیپلوی | `POST /v2/projects/{name}/sources` (آرشیو کد) ← `POST /v2/projects/{name}/releases` |
| وضعیت و لاگ بیلد | `GET /v1/releases/{id}`, `GET /v2/releases/{id}/build-logs` (از سورس CLI) |
| ریلیزها، لاگ، متریک | `GET /v1/projects/{name}/releases`, `/logs`, `/metrics/summary` |
| متغیرهای محیطی | `POST /v1/projects/update-envs` |
| دامنه و SSL | `GET/POST /v1/domains`, `GET /v1/domains/{id}/check`, `POST /v1/domains/provision-ssl-certs` |
| DNS لیارا | `dns-service`: `/api/v1/zones`, `/api/v1/zones/{zone}/dns-records` |
| کاتالوگ پلن‌ها | `GET /v1/me` |

درخواست‌های تغییر از یک منبع مشترک (`packages/liara/src/requests.ts`) ساخته می‌شوند. **همان چیزی که کاربر در کارت تأیید می‌بیند، همان است که ارسال می‌شود.** خواندن‌ها در برابر 429/5xx با backoff دوباره تلاش می‌شوند؛ درخواست‌های تغییر هرگز خودکار تکرار نمی‌شوند.

## ۴. محدودیت‌ها

**محدودیت‌های API لیارا** (در محصول هم در صفحه‌ی «قابلیت‌ها» و داخل هر گزارش اعلام می‌شوند):

- **برگرداندن ریلیز (rollback):** API ندارد. راهنمایی می‌کنیم از کنسول لیارا انجام شود.
- **زمان پاسخ:** متریکی در API نیست. از لاگ درخواست‌ها و چند درخواست آزمایشی اندازه می‌گیریم.
- **قیمت دقیق پلن‌ها:** ساختار کاتالوگ `/v1/me` در مستند API نیامده. اگر خوانده نشد، قیمت تخمینی با برچسب «تخمینی» نشان می‌دهیم.
- **تغییر NS در ایرنیک:** ایرنیک API عمومی ندارد. مقادیر دقیق را می‌دهیم و کاربر خودش انجام می‌دهد.
- **وضعیت داخلی دیتابیس‌های بیرون از لیارا:** قابل مشاهده نیست. فقط اثرش در لاگ اپ (مثل `ECONNREFUSED`) تشخیص داده می‌شود.
- **نوشتن در مخزن گیت‌هاب کاربر:** دسترسی نداریم. اصلاح کد روی نسخه‌ی کاری همان اجرا اعمال و دیپلوی می‌شود و فایل CI را کاربر commit می‌کند.

**محدودیت‌های خود راه‌انداز (صادقانه):**
- با حساب واقعی لیارا هنوز end-to-end اجرا نشده است. کلاینت REST از روی مستند ساخته و با تست قرارداد (fake fetch) آزموده شده؛ اجرای واقعی نیازمند توکن است.
- تشخیص خودکار علت روی ۷ الگوی رایج (پورت، اسکریپت start، متغیر جاافتاده، APP_KEY، نسخه‌ی پکیج، ایمیج داکر، بازنویسی PORT) و نشانه‌های SRE (RAM، CPU، دیتابیس، خطای کد، ریلیز اخیر، کرش مکرر) کار می‌کند. برای موارد ناشناخته شواهد را جمع و راهنمایی می‌کند، نه اصلاح خودکار.
- پایش دوره‌ای داخل خود راه‌انداز اجرا می‌شود (هر ۴ تا ۱۵ ثانیه برای اپ‌های مجاز)، نه سرویس پایش ۲۴ساعته‌ی لیارا.
- حالت شبیه‌سازی (پیش‌فرض) برای دمو است و در رابط کاربری با برچسب «لیارای شبیه‌سازی» مشخص است.

## ۵. اجرا

```bash
pnpm install
cp .env.example .env       # پیش‌فرض: لیارای شبیه‌سازی + مدل شبیه‌سازی، کاملاً آفلاین
pnpm dev                   # http://localhost:3200
pnpm gates                 # lint + typecheck + ۱۱۰+ تست + build
```

حالت واقعی: `LIARA_MODE=real` و `LIARA_API_TOKEN` در `.env`. پیش‌فرض `DRY_RUN=true` است، یعنی فقط فراخوانی‌ها نشان داده می‌شوند. مدل: `LIARA_AI_BASE_URL` و `LIARA_AI_KEY` و/یا `LLM_*`. جزئیات در `CLAUDE.md` و `README.md` آمده است.
